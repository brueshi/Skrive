# Phase 3.3 Diff UI Design

**Status.** Design locked; implementation lands in Phase 3.3a (history sources + line diff) and 3.3b (structural-diff upgrades). This memo is the source of truth for what the diff view looks like and how the user enters, navigates, and exits it.

**Companion docs.**

- [`3.3-algorithm-memo.md`](3.3-algorithm-memo.md) — which algorithm renders the diff.
- [`../planning/phase-3.3-plan.md`](../planning/phase-3.3-plan.md) — the phased implementation plan.

## The thesis

Diff is the feature that turns Skrive's project intelligence into real insight for a writer. Seeing the old document next to the revised one — *"what did I change, and is the new version actually better?"* — is the payoff for all the link-graph and history plumbing beneath it. The UI has to earn that payoff. A diff view that reads as noise is worse than no diff view; a diff view that reads as *the document, revised* is the moment the tool stops being a text editor and starts being a revision surface.

Every design decision below is tuned to one question: **can a reader skim the diff and immediately see what changed, at the level of prose, without decoding?**

## Layout model

### Diff mode is its own layout, mutually exclusive with split

Skrive's tabs have three layout modes today: `raw` (single pane, markdown source), `preview` (single pane, rendered HTML), and `split` (both panes, same file — source on one side, preview on the other). The two-pane surface is already in use for a specific purpose in `split`: seeing one file from two angles.

Diff mode uses the same two-pane surface for a *different* purpose: seeing **two versions** of one file. Those two purposes don't compose. We don't try to.

`LayoutMode` grows two variants:

- `diff-raw` — two panes, both rendering markdown source, before on left + after on right.
- `diff-preview` — two panes, both rendering HTML, before on left + after on right.

Entering diff from `raw` jumps to `diff-raw`. Entering from `preview` jumps to `diff-preview`. Entering from `split` is **not available** — the history panel's "Compare" action is disabled when the active tab is in `split`, with a tooltip: *"Switch to raw or preview to compare versions."* Disabled beats auto-collapse: auto-collapsing someone's carefully-set split view to enable a different mode is the kind of paternalism we reject elsewhere.

Within diff mode, a compact toggle in the header (same visual language as the existing layout-mode toggle) flips between `diff-raw` and `diff-preview`. `split` is greyed out; the tooltip names why. The user's last choice of raw vs preview inside diff is per-tab, persisted.

### Split is always on, divider is resizable

Both panes are *always* shown in diff mode. There's no "unified inline" mode. The entire point is side-by-side comparison; unifying the view loses the whole benefit. This also makes the implementation simpler — one layout shape, two render passes.

The vertical divider between panes uses the same drag handling as the existing `SplitView` component. The ratio persists per-tab, independent of the editor-mode `split` ratio (a user might want 50/50 for diffs and 60/40 for editing; those are different preferences).

### Header chrome during diff mode

The normal per-tab header shrinks to leave room for pane labels:

```
[ tab name ]  |  Before — 2 days ago    After — just now    [raw|preview]  [×]
```

- **Pane labels:** each shows a human-readable timestamp (`just now`, `2 days ago`, `3 Mar 2025`) and on hover reveals the full ISO timestamp plus the source (git commit SHA + message, or `checkpoint`).
- **Mode toggle:** `raw`/`preview` as a two-state switch — `split` is visible but disabled.
- **Close button (×):** exits diff mode, returns to whichever mode the tab was in before (raw or preview).

## Visual language

### Palette: sage + neutral (Option A)

Skrive's palette is warm-first — off-white cream background, brass-toned foreground, muted warm-gray for secondary text. The diff view stays within that family, with one new hue (sage) for additions and typography alone for deletions.

**Additions.** Warm-leaning sage. Enough green to signal "new" without reading as compile-success or git-diff. Pale tint as background, fuller saturation for edge bars.

- Light mode: tint `hsl(95, 20%, 92%)` on background, bar `hsl(100, 15%, 45%)`.
- Dark mode: tint `hsl(95, 15%, 20%)` on background, bar `hsl(100, 22%, 65%)`.

**Deletions.** No hue at all. Strikethrough + 55% opacity. A thin warm-gray left-edge bar carries the "something was here" signal. Deletions should recede visually — the reader cares about what's there *now* more than what was removed.

- Light mode: bar `hsl(30, 8%, 60%)`. No fill.
- Dark mode: bar `hsl(30, 5%, 45%)`. No fill.

**Moved sections.** Cool slate accent, deliberately outside the warm family so moves read as structurally different from edits. At the move's destination: a small pill banner reading *"Moved from earlier"* or *"Moved from later"* depending on direction, plus a gutter arrow. At the move's origin: the content fades to 40% opacity, anchoring the "what used to be here" context.

- Pill background: `hsl(215, 15%, 90%)` (light) / `hsl(215, 10%, 28%)` (dark).
- Pill text: same as `--skrive-muted`.

**Reworded paragraphs.** 2px dashed bar in the accent brass (`--skrive-link` hue). No fill. Within a reworded paragraph, the intra-paragraph word-level diff uses the same add/delete treatment as the block level — sage tints for added words, strikethrough for deleted words.

**Gutter markers.** Quiet unicode glyphs in `--skrive-muted` tone, one per changed block:

- `·` unchanged (a barely-visible nudge, so gutter alignment is readable)
- `+` added
- `−` deleted
- `↕` moved
- `~` reworded

### Typography carries most of the signal

Color assists; it doesn't lead. The prose itself stays in its normal weight and color so the document still reads as a document. Changes are signaled first through:

1. **Weight:** added content can get a slight weight bump (+50 in the font's scale) to draw the eye.
2. **Opacity:** deletions drop to 55%; they fade without disappearing.
3. **Strikethrough:** deletions get a horizontal line.
4. **Left-edge bars:** 2px vertical bars in the margin, per-block, tinted per op kind. This is the peripheral-scan cue — the eye catches bars before it reads text.

Color is the *fourth* signal, used as a soft tint, not a highlight. If the app were rendered in grayscale, the diff would still be legible.

### Dark mode

Same hues, inverted lightness. Sage becomes a deeper forest accent against the true-dark background; the brass bars pick up a warmer glow. Contrast ratios verified against WCAG AA for body text in both modes.

## Operation rendering

Five operations emerge from the diff algorithm — how each one looks in raw mode versus preview mode:

### Kept

Block is byte-identical in both versions. Renders unchanged in both panes with a quiet `·` gutter marker. No bar, no tint, no weight change. The reader's eye skates past.

### Added

Block exists only in the `after` version.

- **Raw mode:** only the after pane shows the block, with a sage tint background and sage left bar. The before pane shows a subtle placeholder gap of the same height (so both panes' gutters stay aligned). Gutter marker: `+`.
- **Preview mode:** same, but the rendered HTML inside the after pane gets the sage background. The placeholder in the before pane is rendered as a thin dashed `hsl(95, 20%, 80%)` rule labeled with a small *"added"* chip — preserves scroll alignment without leaving a visual hole.

### Deleted

Block exists only in the `before` version.

- **Raw mode:** only the before pane shows the block, with strikethrough + 55% opacity + a warm-gray left bar. The after pane shows an aligned placeholder gap.
- **Preview mode:** same — the before pane's rendered HTML gets the strikethrough treatment at the block level (the `<p>` gets `text-decoration: line-through` + opacity), plus a small *"deleted"* chip inline at the block's leading edge.

### Moved

Block content is identical but its position shifted. Both panes show the block; they anchor it at different scroll positions.

- **Raw and preview modes:** at the new position, a cool-slate pill banner at the block's top margin (*"Moved from §2 earlier"*) and a gutter arrow `↕`. At the old position, the content fades to 40% opacity with an *"Moved to §3 later"* chip. Clicking either banner jumps the scroll of both panes so the matched blocks align visually.

### Reworded

Block content changed but the match score is below the "distinct blocks" threshold — same paragraph, different words.

- **Raw mode:** both panes show the block. Each pane gets a dashed brass left bar. Intra-block word-level diff is applied: added words (in the after pane) get sage tint; deleted words (in the before pane) get strikethrough. The gutter marker is `~`.
- **Preview mode:** the rendered prose carries the intra-paragraph diff inline, with added phrases tinted and deleted phrases struck through. The reader sees the paragraph *as revised*, with the deltas legible as part of the prose.

## Sync scroll

The two panes scroll in tandem, with the topology-aware model described below. A small toggle in the header ({linear | matched}) flips between:

**Matched-block scroll (default).** When the user scrolls one pane, the other pane scrolls such that the *matched block* stays aligned horizontally. For blocks that moved, this means the panes don't track line-for-line — instead, scrolling to a block on the left pane jumps the right pane to the same block's new position. Add/delete blocks have placeholder gaps in the opposite pane; scrolling through one pane scrolls over the gaps in the other.

**Linear scroll.** Simple geometric sync: the two panes scroll as if stacked side-by-side, pixel-for-pixel. Useful when the diff has few or no moves; some users just want raw alignment. Available as a toggle; default is matched.

Edge cases:

- **Unmatched tail blocks.** If the after version has more blocks than the before (or vice versa), scrolling past the last matched block falls back to linear for the tail.
- **Rapid scrolling.** The matched-block scroll shouldn't feel "grabby." If the user scrolls fast, we throttle re-alignment to every ~120ms so the right pane catches up without jittering.

## Navigation through changes

Keyboard shortcuts for jumping between change hunks, modeled on how long-form reviewers navigate code diffs:

- `n` or `j` — next change (scrolls both panes to the next changed block after the current scroll position).
- `p` or `k` — previous change.
- `Home` — first change.
- `End` — last change.
- `Escape` — exit diff mode.

A small "3 of 12" indicator in the header shows which change the user is currently viewing. Unchanged blocks are skipped; kept is invisible in the counter.

## Version selection

Entry points to diff mode:

1. **History panel → single click.** Shows *that version* vs the current file. The common case: "what changed between the last commit and now?" Works in git mode and checkpoint mode identically.
2. **History panel → click, then shift-click another entry.** Shows *those two versions* — lets the user compare any two historical points without current-file involvement.
3. **From a backlink or search result.** Out of scope for Phase 3.3. Not a natural entry point.

The history panel itself renders the per-file version timeline — entries in reverse chronological order, with source badges (`git` commit sha + message, or `checkpoint` with manual name if any, or an auto-checkpoint timestamp). Clicking an entry enters diff mode; shift-clicking lets you pin a baseline for pairwise compare.

## Interactions we are not shipping

Recorded so we don't relitigate in implementation.

- **Editing inside diff view.** Diff is read-only. Wanted to edit? Exit diff, you're back in the normal file.
- **Unified inline diff** (single pane, interleaved old and new). Cut. Side-by-side is the whole point.
- **Three-way diff** (before + after + current, for conflict resolution). Skrive is not a git client. Out of scope.
- **Diff across files** (compare `a.md` vs `b.md`). Different feature, different product question, possibly never.
- **Comments or annotations inside the diff.** Collaboration feature; not in the build outline.
- **Per-hunk accept/reject** (like a selective merge). Read-only view; the file you want is either before or after, picked via the history panel.
- **Blame / per-line attribution.** Out of scope — Skrive doesn't track authorship.

## Rejected alternatives

**Palette Option B — monochrome.** Pure typography and opacity, no hues. Too subtle for peripheral scanning; the eye doesn't catch changes in a long document without *some* hue delta. Cut.

**Palette Option C — full warm family.** Honey / dusty rose / lavender / brass. Four hues compete for attention and the diff reads as busy. Also, dusty rose is close enough to the red-family that it introduces the exact association we're trying to avoid. Cut.

**Diff view as a modal overlay rather than a layout mode.** Would let any tab state (including split) launch a diff over top. Rejected: modals break the "your tabs are your workspace" mental model, the Esc-to-close dynamic is wrong for a reading surface, and the chrome doesn't compose with existing tab/header conventions. Layout mode wins.

**Auto-collapse split to raw on diff entry.** Considered and rejected for paternalism reasons. Disabled-with-tooltip is the right signal: it tells the user *"this action isn't available from here"* without silently undoing their other choices.

**Raw and preview side-by-side in diff** (four panes: before-raw + before-preview + after-raw + after-preview). Rejected: density collapses readability. The two-pane maximum is a feature, not a limitation.

## Open questions for implementation

Tracked here so implementation spots them; not gating this memo.

1. **Scroll sync performance on long documents.** Matched-block mapping is O(n) per scroll event; at a few hundred blocks that's fine. Worth measuring on a 5000-block document if dogfooding surfaces one.
2. **Word-level diff cost inside reworded paragraphs.** Using `similar` per paragraph is cheap. For paragraphs with high word count (500+ words, rare in prose), might want a threshold to fall back to paragraph-level only.
3. **Rendering annotated HTML in preview mode.** Either we wrap `marked`'s output with a post-render walker that injects diff annotations, or we pre-insert marker elements into the markdown source before parsing. First is cleaner; second is faster. Decide at implementation.
4. **Dark-mode hue values** need to be checked against an actual dark-mode render, not just HSL math. Tweak during implementation.

## What this memo commits us to

- Diff mode is its own `LayoutMode` (`diff-raw` and `diff-preview`), launched from single-pane modes only.
- Always split. Before on left, after on right. Resizable divider.
- Sage for adds, no-hue-for-deletes, slate for moves, brass-dashed for rewordings.
- Typography carries most of the signal; color assists.
- Matched-block sync scroll by default, linear as a toggle.
- Read-only. `n`/`p` navigate. `Esc` exits.
- History panel is the entry point; single-click diffs vs current, shift-click pins two versions.

Implementation inherits these. Deviation without amending this memo is a bug.
