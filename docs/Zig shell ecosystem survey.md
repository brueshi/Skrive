# Zig Shell Ecosystem Survey

**Status.** Research complete, 2026-06-10. Companion to `Zig shell audit.md` — that doc establishes what Skrive needs from a Zig shell; this one establishes what exists to build it from. All repo facts below were verified against live repos/docs this week (activity dates are actual commit timestamps, not README claims). Anything unverifiable is flagged inline.

**The two headline finds.**

1. **The architecture already shipped.** `vercel-labs/zero-native` (Apache-2.0, 4.1k stars, v0.2.0 on 2026-05-13, Zig 0.16) is a Zig desktop shell for web frontends: system webview (WKWebView/WebKitGTK/WebView2) or optional bundled CEF, a custom `zero://app` scheme, a typed `window.zero.invoke()` bridge with payload size limits, origin checks, and a per-command permission manifest. It is pre-release, its Windows path is young, it has no titlebar customization yet, and it is a Vercel Labs experiment (historically abandonable) — so it is prior art to *read*, not a foundation to *adopt*. But it removes "is this architecture sane" from the question list. Someone well-funded reached the same conclusions: Zig core, system webview, JSON bridge with a closed command table, C++ host on Windows.

2. **The strongest macOS pattern is Ghostty's, not webview bindings.** Ghostty (MIT, 56k stars) is a Zig core compiled as a C-ABI library (`ghostty.h` + a modulemap so Swift imports it cleanly) with a *Swift/AppKit shell* owning all platform UI. Mitchell Hashimoto documented the pattern directly in "Integrating Zig and SwiftUI" and even he did not write the Mac shell in Zig. For Skrive the pattern inverts perfectly: a small Swift shell owns the window and WKWebView (where `WKURLSchemeHandler`, `WKScriptMessageHandler`, `evaluateJavaScript`, and `titlebarAppearsTransparent`/`fullSizeContentView` — the inset-chrome look — are all first-class), and the Zig core does dispatch, FS, watching, and search behind a C ABI.

## 1. The webview layer — verified options

| Path | Status (verified) | Verdict for Skrive |
|---|---|---|
| `webview/webview` (C/C++ core) | MIT, 14.1k stars, **dormant**: last release 0.12.0 (Sep 2024); 2025-26 commits are docs-only. **No custom schemes** — issue #851 open since Nov 2022. | `thechampagne/webview-zig` | MIT, 191 stars, pinned to Zig 0.13 (two stable releases behind), last commit 2025-12. | Stale. Skip. |
| Turf (`awesomo4000/turf`) | **No license file** (legal blocker), dormant since 2025-09, Windows support is an unmerged branch contradicting its announcement. | Skip. |

| WebUI / `zig-webui` | Both MIT and genuinely active (2026-05/06). But the model is "launch the user's installed browser, talk over a localhost WebSocket" — browser-window chrome, localhost origin, connect-to-page lifecycle. | Shape mismatch for a polished document editor. Right tool for dashboards/utility panels. |
| `mitchellh/zig-objc` | MIT, maintained (Zig 0.16 compat merged 2026-04), Ghostty dependency, supports msgSend with typed returns, subclass creation, and **blocks with captures** (what `evaluateJavaScript:completionHandler:` needs). | `marlersoft/zigwin32` | MIT, maintained (2026-04). **WebView2 is not in it** — zero `ICoreWebView2` hits; WebView2 ships as a separate NuGet SDK outside win32metadata. | Gives windowing + COM plumbing only. Every existing Zig-drives-WebView2-directly example is a 0-13 star hand-rolled-vtable experiment. |

**Conclusion (a) macOS:** Ghostty pattern (Swift shell + Zig C-ABI core) first; pure Zig via zig-objc second. Both verified viable; the first is verified *at scale*.

**Conclusion (b) Windows:** thin C++ host wrapping WebView2's COM API, exposing a C ABI to the shared Zig core — which is exactly what zero-native chose (`webview2_host.cpp`) despite being the best-funded Zig-native project in existence. That choice is the strongest available signal about where the ergonomic line sits. No maintained Zig WebView2 binding exists, full stop.

**The resulting shape:** per-platform native host, ~hundreds of lines each (Swift on macOS, C++ on Windows), owning window + webview + scheme handler + message pump; one shared Zig core owning the command dispatcher, FS sandbox, watcher integration, search/snapshot logic. Symmetric, and each half uses the language its platform actually documents.

## 2. Secure context and clipboard — the audit's open question, now answered

The audit flagged "custom schemes may not be secure contexts" as Spike 1's gating unknown. Verified answer: **WKWebView custom schemes are NOT secure contexts**, and https-or-secure pages cannot even fetch from custom-scheme URLs (mixed-content-style blocking — wry issue #946: "no amount of CORS/CSP headers" fixes it). The only direct escape is the private `WKProcessPool._registerURLSchemeAsSecure:` — works today, prohibited in the Mac App Store, can break on any OS update. Tauri's production answer is per-platform: the app origin is a custom scheme on macOS and a **localhost-mapped origin on Windows** (`http://tauri.localhost` via `AddWebResourceRequestedFilter` + `WebResourceRequested` interception — WebView2 has no true scheme registration in this path; localhost is a potentially-trustworthy origin, which is how secure context is obtained there).

Consequences for Skrive, concretely:

- **`navigator.clipboard` cannot be assumed.** The preview's rich copy path (`app/src/components/editor/clipboard.ts`, HTML + plain text payloads) needs a bridge command (`clipboard:writeRich`) in a Zig-shell world — NSPasteboard / Windows clipboard on the native side. This is what Tauri apps do. Cheap to add to the Electron contract now as part of Stage 0, so the frontend stops depending on a web API that won't be there.
- **Serving strategy is a real decision, not a detail.** Options, in rough order of preference: (1) `loadFileURL(_:allowingReadAccessTo:)` pointing at the embedded-or-extracted dist — WebKit treats file origins as locally trustworthy, at the cost of file-origin fetch quirks; (2) custom scheme + accept non-secure-context and route every gated API through the bridge; (3) localhost server (std.http.Server is fine for a single trusted loopback client) — secure context via `http://127.0.0.1`, at the cost of a port and a lifetime to manage. Spike 1's job narrows from "discover the constraint" to "pick between three known shapes."
- **Storage location is uncontrollable on macOS.** WKWebView localStorage/IndexedDB lands under `~/Library/WebKit/<bundle-id>/` no matter what; `WKWebsiteDataStore(forIdentifier:)` (macOS 14+) is the only partitioning control. Skrive keeps canonical state on the native side already (the audit's persistence namespace) — keep it that way; treat webview storage as cache only. A wry changelog entry records a Linux IndexedDB path change that *lost user data* across an upgrade — the cautionary tale.

## 3. Drop-in libraries for the shell primitives

## 4. Zig itself — toolchain state, June 2026

- **Current stable: 0.16.0 (2026-04-13).** Cadence is a breaking major every 6-8 months, and the last two were earthquakes in exactly this app's subsystems: 0.15 "Writergate" replaced all std readers/writers; 0.16's "Io migration" made essentially all I/O take an explicit `Io` parameter (`std.Io.Dir`/`std.Io.File`, `std.process.spawn(io, ...)`), split `@Type`, and moved `@cImport` into the build system. Ghostty — the flagship — deliberately runs a full version behind (1.3.0 requires 0.15; 0.16 migration is an open issue). TigerBeetle pins exact compiler versions. Do the same. Also note Zig's canonical repo moved to Codeberg (2025-11); GitHub is a mirror.
- **The good news, verified per audit need:** `std.json.parseFromSlice` into typed structs **rejects unknown fields by default** (exactly right for the IPC envelope; `parseFromValue` enables two-stage envelope-then-payload parsing). Atomic writes are first-class (`createFileAtomic`, write-then-replace — the same tmp+fsync+rename pattern as `atomic-write.ts`). `std.process.spawn` covers the git history backend. `@embedFile` plus a ~50-line build step that generates a path→file manifest covers embedding `dist/` (community helpers exist; you'd write it yourself).
- **The gaps, verified:** **no file watching in std at all** (the build system grew a private watcher for `zig build --watch`; the issue to extract it into std is milestoned "unplanned") — hence e-dant/watcher above. std.http.Server is officially "very slow and assumes well-behaved clients" — irrelevant for a loopback-only single-client use, disqualifying for anything else. translate-c was rewritten on arocc (a young C compiler in Zig) in 0.16 — Apple's clang-extension-heavy headers through it is an unverified maturity question; zig-objc sidesteps this by using the plain-C objc runtime API rather than parsing Apple headers.
- **Cross-compilation:** building natively on the Mac with Xcode CLT is the easy path for the macOS target. Plain Win32 Zig code cross-compiles from macOS cleanly (the marquee feature), but **WebView2 specifically does not**: the loader is an MSVC-flavored static lib outside the Windows SDK, so the workable pattern is dynamic-loading `WebView2Loader.dll` at runtime — and realistically, CI builds Windows on Windows anyway (the audit already assumed a per-OS matrix for packaging).
- **The sober data point:** Bun merged its Zig-to-Rust core rewrite on 2026-05-14 (~1M lines, largely agent-generated), citing persistent use-after-free/leak classes in long-lived manual-memory code. Bun's scale and pace are nothing like a 3-4k-line shell, and TigerBeetle demonstrates the discipline works when scope stays small — but Zig's biggest commercial flagship exiting is exactly the kind of evidence the experiment docs say not to rationalize away. It sharpens the case for keeping the Zig surface minimal (shell primitives only, business logic stays in JS per the audit's option 2) rather than letting the core grow ambitions.

## 5. Alternative engines — the horizon shelf

Verified verdicts, calibrated specifically on "can it host ProseMirror" (contenteditable + beforeinput + composition/IME + Selection fidelity) and typography:

| Engine | ProseMirror today | The verified one-liner |
|---|---|---|
| System WKWebView / WebView2 | **Yes** | The only sane default. WebView2 evergreen is preinstalled on Win 11, supported on Win 10 22H2 **through at least Oct 2028**; fixed-version now exceeds 250MB — non-starter. |
| CEF | **Yes** | The consistency lever: ~80-120MB/app, BSD, and Chromium explicitly does not support stripped builds — so it is "Electron minus 30-50%," never minus 90%. If Spike 1's typography eyeball gate *fails* (Core Text Fraunces unacceptable vs today's Chromium rendering), CEF — or zero-native's webview/CEF dual-backend idea — is the documented fallback that preserves the Zig shell while restoring pixel-identical text. |
| Ultralight 1.4 | **No** | WebKit fork at Safari 16.4 level, YC-backed, now $3k/yr/app Pro tier with an explicitly feature-limited free tier. Disqualified on one fact: **no IME support** (their own issue tracker). A text editor cannot ship without composition input. Game UI tool. |
| Sciter | **No** | Not a real DOM; actual React crashes on hello-world (its "React" is Reactor, a native JSX reimplementation). |
| Servo | **Not yet — the genuine 3-5 year bet** | Revival is real: LF Europe funding, monthly releases, `cargo add servo` since 0.1.0 (2026-04-13). But contenteditable is barely begun (the tracking issue's recent movement is a PR exposing the *attribute*, reviewer-noted as not actually supporting editing). Verso the browser was archived 2025-10; `tauri-runtime-verso` lives on. Rust-only embedding API; a C ABI is unverified/unplanned. Watch annually; do not build on it. |
| Blitz (Dioxus) | **No by design** | Modular Rust HTML/CSS renderer (Stylo+Taffy+Parley+Vello), alpha, deliberately no script/DOM. Irrelevant for the editor; *conceivably* interesting someday for a print/export pane. |
| Electrobun | Adjacent prior art | TS apps on Bun + Zig bindings + system webview, ~12-14MB bundles, v1 Feb 2026 — but its Zig binding layer is now downstream of Bun's Rust rewrite. A thing to learn from, not use. |

Strategic restatement of the audit's F2 with this table in hand: every row that can host ProseMirror is a browser engine. The webview ceiling is unbreached on every horizon that supports rich text editing — Servo is the only future entrant even aimed at it, years out. The Zig shell remains a Chromium-tax play, and the ledger remains the separate instrument it was designed to be.

## 6. What this changes in the audit's roadmap

The audit's stages survive intact; the spikes get sharper:

- **Stage 0 addition:** add `clipboard:writeRich`/`readText` bridge commands to the Electron contract and migrate `clipboard.ts` off raw `navigator.clipboard` (section 2 — it will not survive the move otherwise). Everything else in Stage 0 stands.
- **Spike 1 (macOS) now has a concrete bill of materials:** Swift shell (~300 lines: NSWindow with `titlebarAppearsTransparent`, WKWebView, `WKURLSchemeHandler` or `loadFileURL`, `WKScriptMessageHandler` in, `evaluateJavaScript` out) + Zig core as C-ABI static lib (std.json envelope dispatch, stub project). Before writing it, read zero-native's `appkit_host.m` and permission-manifest design, and Ghostty's `include/ghostty.h` + modulemap for the boundary idiom. Decision to make inside the spike: serving shape (file URL vs custom scheme vs loopback) — section 2 gives the three known options; pick by testing the lint worker, storage, and clipboard-via-bridge against each.
- **Spike 1 alternative track, time-boxed to one evening:** `happystraw/zig-webview` hello-world loading the Skrive bundle — purely to calibrate how far the cheap path gets before hitting the no-custom-scheme/no-chrome wall. Knowing the wall's exact location is worth three hours, not more.
- **Spike 3 (watcher) de-risked:** prototype = link `watcher-c`, translate events to the existing `ProjectChange` shape, add the write-finish debounce. The platform-backend invention the audit budgeted for is now integration work.
- **Spike 4 (Windows) shape decided in advance:** C++ host (zero-native's pattern), evergreen WebView2 with bootstrapper detection, localhost-mapped or `WebResourceRequested`-intercepted origin per Tauri's precedent. Raw-Zig COM is explicitly rejected — every survey hit doing it is an abandoned experiment.
- **Updater (post-graduation) de-risked:** Sparkle + WinSparkle on a shared CI-generated appcast, enclosures on GitHub Releases — compatible with the existing draft-release workflow.
