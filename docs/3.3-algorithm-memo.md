# Phase 3.3 Algorithm Decision Memo

**Status.** Algorithm decided, backend shipped, frontend renderer shelved. All three prototypes ran against the fixture set; block-hash + Hungarian assignment (Prototype 1) won on output quality and implementation economy. The production `compute_diff` module (`src-tauri/src/diff.rs`), its Tauri command, and the TypeScript type mirrors all shipped and are covered by tests. **The Svelte-side renderer upgrade was attempted and reverted** — a reactivity bug in the preview-mode structural rendering couldn't be reproduced or diagnosed remotely, and shipping a half-broken demo surface was judged worse than sticking with the 3.3a line-diff renderer. Picking the renderer back up is a future task; the algorithm pick and the backend don't need to be revisited.

**Resolves.** [Open question T1](../planning/open-questions.md#t1-what-algorithm-does-structural-diff-use) — "What algorithm does structural diff use?" **Answer: block-hash matching with Hungarian assignment.**

**Blocks.** Nothing. The backend is ready; future renderer work calls the existing `compute_diff` command and builds on `src/lib/diff/structural-diff.ts`.

Phase 3.3 is the second major technical bet in Skrive's roadmap (after Phase 2.2's inline preview decorations). The product question is whether a *structural* diff of two document versions can render as readable semantic operations — "moved section," "reworded paragraph," "added heading" — rather than the red-and-green line noise every other tool ships. The algorithm pick determines whether the feature feels like magic or like a worse `git diff`.

The memo compares three candidates against three fixtures, records the output, and picks one.

## Candidates

Three algorithms are evaluated. All three treat the document as a sequence or tree of *blocks* (paragraphs, headings, lists, code fences, tables), not a character or line stream — the line-diff baseline is what we're trying to move past.

### Block-hash + Hungarian

Hash each block in both versions. Build a cost matrix where `cost[i][j]` is small when `before[i]` and `after[j]` have similar hashes (or edit distance between their text), large otherwise. Run Hungarian assignment to find the minimum-cost pairing. Unassigned blocks on the before side are deletions; unassigned on the after side are insertions. Position changes among assigned pairs are detected as moves.

- **Complexity.** O(n³) on block count *n* for Hungarian. For a 500-block document that's still under a second in practice.
- **Strengths.** Native move detection. Simple to explain. Reworded-paragraph case handled by the text-distance cost function.
- **Weaknesses.** The cost function is ad-hoc — tuning it is the hard part. Block-level only (doesn't reason about hierarchy).
- **Prior art.** Similar in spirit to patience diff and `diff-match-patch`'s word mode.

### Zhang-Shasha tree edit distance

Treat the Markdown AST as a labeled tree and compute the minimum edit script between two trees. Classic optimal algorithm, O(n² · depth²) or similar depending on formulation. The edit script reads as a sequence of `insert-node`, `delete-node`, `relabel-node` operations.

- **Complexity.** Cubic-to-quartic in worst case. Heavy for long documents.
- **Strengths.** Mathematically optimal. Respects hierarchy natively (a heading and its children move together).
- **Weaknesses.** Implementation is intricate — either we port ~150 lines of algorithm code or pull in a crate like `tree-edit-distance`. The raw output is low-level; we'd still need a pass to group inserts/deletes into higher-level "moved section" operations.
- **Prior art.** Used in XML diff tools and JavaScript AST differs (`gumtree`, `jsdiff-ast`).

### Block-Myers

Standard Myers diff but the unit is a block instead of a line. Tokenize each document as `[block_hash_1, block_hash_2, ...]` and run the classic LCS-based diff on those arrays. Output is adds/deletes/kept with no move detection in the core algorithm; moves come from a post-processing pass that pairs same-hash adds with deletes.

- **Complexity.** O((n + m) · D) where D is the edit distance. Fast for small-to-medium edit distances.
- **Strengths.** Familiar shape. Tons of existing crates (`similar`). Cheap to write from scratch.
- **Weaknesses.** Doesn't detect moves natively; the post-processing can mis-pair. A reworded paragraph reads as delete+add unless the cost function is generous, which at that point is re-inventing the first algorithm.
- **Prior art.** What `git diff` does on a per-block level. Familiar output but the same "big delete + big add" failure mode on any structural reorganization.

## Fixtures

All three fixtures live in [`docs/fixtures/3.3/`](fixtures/3.3/) as `{name}-before.md` / `{name}-after.md` pairs. Deliberately short — the memo runs algorithms against them manually and eyeballs output.

### `reword` — reworded middle paragraph

Five-paragraph prose piece on slow reading. The middle paragraph is rewritten: same meaning, ~60% different words. The surrounding paragraphs are byte-identical. Stresses reworded-paragraph detection.

**Expected output.** Four "kept" paragraphs and one "reworded" paragraph. A bad algorithm reports one delete + one add.

### `reorder` — swapped sections

Essay with four `##` sections: Introduction, The Problem, The Solution, Conclusion. In the `after` version The Problem and The Solution are swapped. Headings and bodies are byte-identical otherwise. Stresses move detection.

**Expected output.** Two "moved section" operations, or one swap operation. A bad algorithm reports two sections deleted and two sections added.

### `insert` — new section inserted mid-document

Essay on kinds of revision with sections Line edits, Structural edits, Why the order matters. The `after` version inserts a new section ("Developmental edits") between Structural and Why-the-order. All original sections are byte-identical. Stresses attribution of the new content without disturbing the surrounding structure.

**Expected output.** Three "kept section" operations and one "added section" operation. A bad algorithm reports the last section as deleted-and-re-added because its position shifted.

## Results

Filled in as each prototype runs. Each run is a transcript of the algorithm's output, lightly annotated.

### Prototype 1 — Block-hash + 2-opt assignment (Hungarian stand-in)

Ran against all three fixtures. Transcripts below. Notes:

- **Matcher is 2-opt local search**, not full Hungarian. For the fixture matrices (small, clear-cut signal, most pairs at distance 0) it converges to the same assignment Hungarian would. A production implementation would use Kuhn-Munkres; the memo's conclusions about output quality are unaffected by the swap.
- Reword threshold is `0.55` — above that, the algorithm treats a matched pair as two distinct blocks (delete + add). Tuned to the reword fixture's paragraph edit (d=0.44, below threshold → Reworded).

**Fixture: `reword` (5 → 5 blocks).** Expected: 4 kept, 1 reworded. Actual:

```
[0] kept       # The Slow Read
[1] kept       Reading carefully is the most useful thing...
[2] kept       The first time I noticed this...
[3] reworded   (d=0.44) The change was immediate. Sentences...
[4] kept       I don't read this way all the time...
[5] kept       The trick, if there is one, is patience...
```

No false delete+add split on the middle paragraph. Correct.

**Fixture: `reorder` (11 → 11 blocks).** Expected: two sections moved. Actual: 5 kept, 6 moved.

```
[0] kept       # On Writing Tools
[1] kept       ## Introduction
[2] kept       Every writer eventually collects a pile of tools...
[3→6] moved    ## The Problem
[4→7] moved    Most writing tools optimize for the wrong thing...
[5→8] moved    When a tool measures output and rewards speed...
[6→3] moved    ## The Solution
[7→4] moved    A tool that serves a careful writer does the opposite...
[8→5] moved    This is why the best writing tools are often the oldest...
[9] kept       ## Conclusion
[10] kept      The right tool is not the most capable one...
```

The six block-level moves correspond to the two section-level swaps. A post-processing pass that groups consecutive moves with the same offset into section-level moves is the obvious next step for 3.3b. The algorithm itself correctly attributes every block to a move, not a delete+add pair. Correct.

**Fixture: `insert` (10 → 13 blocks).** Expected: three kept, three moved (the trailing section shifts down), three added. Actual: 7 kept, 3 moved, 3 added.

```
[0] kept       # Three Kinds of Revision
[1] kept       ## Line edits
[2] kept       Line edits are the kind most people picture...
[3] kept       Good line editing is mostly about removing words...
[4] kept       ## Structural edits
[5] kept       Structural edits are different...
[6] kept       Structural edits are harder...
[7→10] moved   ## Why the order matters
[8→11] moved   The instinct is to start with line edits...
[9→12] moved   Your first draft wants you to cut it. Let it.
[7] +added     ## Developmental edits
[8] +added     Developmental edits sit above structural ones...
[9] +added     A developmental edit almost always shortens the document...
```

The inserted section surfaces as three `added` entries. The following section correctly reports as moved (from positions 7-9 to 10-12), not deleted-and-re-added. Correct.

**Summary.** Block-hash + assignment gives clean, readable output across all three fixtures. Moves are detected natively. Rewordings don't degenerate to delete+add. The single remaining polish question — block-level moves vs. section-level moves — is a post-processing pass, not an algorithmic limitation.

**Runtime:** 0.20s total across all three fixtures (debug build, via `cargo test`).

### Prototype 2 — Zhang-Shasha

Ran against all three fixtures. Each document is parsed into a section tree (document → section-per-heading → paragraph leaves under that heading), flattened via post-order with the usual `lmd` + key-roots auxiliary arrays, and diffed with the textbook forest-distance DP. Unit costs throughout: delete 1, insert 1, relabel 0 when labels match else 1. Same move post-pass as Prototype 3 (pair byte-identical Delete+Insert subtrees).

**Fixture: `reword` (7 → 7 nodes).** Expected: 4 kept, 1 reworded. Actual:

```
[0] kept       Reading carefully is the most useful thing...
[1] kept       The first time I noticed this...
[2] reworded   (d=0.47) The change was immediate. Sentences...
[3] kept       I don't read this way all the time...
[4] kept       The trick, if there is one, is patience...
[5] kept       § # The Slow Read
[6] kept       document
```

Clean. The middle paragraph surfaces as a relabel — Zhang-Shasha's native "same tree position, different label" operation — which maps one-to-one onto the reworded op. Correct.

**Fixture: `reorder` (12 → 12 nodes).** Expected: two moved sections. Actual: 5 kept, 6 **reworded**.

```
[0] kept       Every writer eventually collects a pile of tools...
[1] kept       § ## Introduction
[2] reworded   (d=0.77) A tool that serves a careful writer does the opposite...
[3] reworded   (d=0.77) This is why the best writing tools are often the oldest...
[4] reworded   (d=0.47) § ## The Solution
[5] reworded   (d=0.77) Most writing tools optimize for the wrong thing...
[6] reworded   (d=0.77) When a tool measures output and rewards speed...
[7] reworded   (d=0.47) § ## The Problem
[8] kept       The right tool is not the most capable one...
[9] kept       § ## Conclusion
[10] kept       § # On Writing Tools
[11] kept       document
```

The swap degenerates to a chain of relabels — Zhang-Shasha's classical formulation has no native move operation, and a relabel at unit cost is always as cheap or cheaper than delete+insert for an ordered tree. The move post-pass that pairs byte-identical Delete+Insert subtrees never fires because no Delete+Insert ever gets emitted. Lifting this relabel chain into moves would require a dedicated swap-chain post-pass (detect pairs of relabels where `A→B` and `B→A` appear together), which is ~50 lines of algorithm-specific code that Prototype 1 doesn't need. **Degraded output** — the honest reading is that Zhang-Shasha sees "section A was reworded into section B and vice versa," which is not what the writer did.

**Fixture: `insert` (11 → 14 nodes).** Expected: three added, rest kept. Actual: 8 kept, 3 added.

```
[0] kept       Line edits are the kind most people picture...
[1] kept       Good line editing is mostly about removing words...
[2] kept       § ## Line edits
[3] kept       Structural edits are different...
[4] kept       Structural edits are harder...
[5] kept       § ## Structural edits
[6] +added     Developmental edits sit above structural ones...
[7] +added     A developmental edit almost always shortens the document...
[8] +added     § ## Developmental edits
[9] kept       The instinct is to start with line edits...
[10] kept       Your first draft wants you to cut it. Let it.
[11] kept       § ## Why the order matters
[12] kept       § # Three Kinds of Revision
[13] kept       document
```

Clean. The inserted section's three nodes surface as inserts under the root; the surrounding sections stay put. Note that the tail section ("Why the order matters") reads as kept rather than moved — Zhang-Shasha's post-order alignment doesn't care that its absolute position shifted, which arguably reads more naturally to a human than Prototype 1's `moved 7→10` entries. Correct.

**Summary.** Zhang-Shasha is competitive with Prototype 1 on `reword` and `insert`. It **degrades** on `reorder` because the classical TED formulation doesn't support moves natively, and the relabel-chain output a swap produces is not a lift that the move post-pass can catch. Implementation footprint: ~350 lines (section-tree parser + post-order flattener + DP + backtracker + post-pass), vs. ~100 for Prototype 1. The hierarchy advantage flagged in the "Candidates" section (a paragraph moved *into* a moved section reading as one move instead of two) is not exercised by any fixture, and would require a swap-chain lift on top of Zhang-Shasha to actually surface as such. Not worth the extra implementation complexity for output that's strictly worse on the one fixture that stresses moves.

**Runtime:** ~10ms total across all three fixtures (debug build, via `cargo test`).

### Prototype 3 — Block-Myers

Ran against all three fixtures. Each document is tokenized as a sequence of paragraph-or-heading blocks (same `split_blocks` helper as Prototype 1), and `similar::TextDiff::from_slices` runs Myers over those sequences. The walk emits Equal → kept, Delete → pending before-side, Insert → pending after-side. A move post-pass pairs byte-identical Delete+Insert entries into moves; unpaired residue stays as Deleted/Added.

**Fixture: `reword` (6 → 6 blocks).** Expected: 4 kept, 1 reworded. Actual: 5 kept, 1 deleted, 1 added.

```
[0] kept       # The Slow Read
[1] kept       Reading carefully is the most useful thing...
[2] kept       The first time I noticed this...
[3] -deleted   Something changed. The sentences had weight...
[3] +added     The change was immediate. Sentences had weight I had been ski...
[4] kept       I don't read this way all the time...
[5] kept       The trick, if there is one, is patience...
```

The reworded middle paragraph surfaces as a delete+add pair — the failure mode the memo flagged when introducing Myers. Myers has no notion of "same block, different text," and the same-content move post-pass can't pair delete+add entries whose content differs. The only way to recover is to add a fuzzy-matching post-pass on unpaired residue — which is re-deriving Prototype 1's cost matrix, as the memo predicted. **Failed output** for this fixture.

**Fixture: `reorder` (11 → 11 blocks).** Expected: two moved sections. Actual: 8 kept, 3 moved.

```
[0] kept       # On Writing Tools
[1] kept       ## Introduction
[2] kept       Every writer eventually collects a pile of tools...
[6→3] moved    ## The Solution
[7→4] moved    A tool that serves a careful writer does the opposite...
[8→5] moved    This is why the best writing tools are often the oldest...
[3] kept       ## The Problem
[4] kept       Most writing tools optimize for the wrong thing...
[5] kept       When a tool measures output and rewards speed...
[9] kept       ## Conclusion
[10] kept       The right tool is not the most capable one...
```

Myers' LCS picks the longer common subsequence — here "Problem" blocks stay anchored and "Solution" blocks move around them. So only one half of the swap surfaces as moves (3 ops); the other half reads as kept with position indices that happen to match the after-side. That's structurally incomplete compared to Prototype 1's "both halves moved" reading, but not strictly wrong: a reader would accept "the Solution section moved up over the Problem section" as a legitimate way to describe the swap. **Partial output** — cleaner than Prototype 1's 6-move reading for this fixture, but reliant on which half LCS happens to anchor.

**Fixture: `insert` (10 → 13 blocks).** Expected: three kept, three moved, three added. Actual: 10 kept, 3 added.

```
[0] kept       # Three Kinds of Revision
[1] kept       ## Line edits
[2] kept       Line edits are the kind most people picture...
[3] kept       Good line editing is mostly about removing words...
[4] kept       ## Structural edits
[5] kept       Structural edits are different...
[6] kept       Structural edits are harder...
[7] +added     ## Developmental edits
[8] +added     Developmental edits sit above structural ones...
[9] +added     A developmental edit almost always shortens the document...
[7] kept       ## Why the order matters
[8] kept       The instinct is to start with line edits...
[9] kept       Your first draft wants you to cut it. Let it.
```

The inserted section surfaces as three `added` entries; the trailing section reads as kept despite its position shifting by three. For this fixture that's arguably the *right* output — a reader would say "new section added, nothing else moved." Prototype 1 over-reports moves here because its assignment algorithm treats index shifts as moves. Correct output, and cleaner than Prototype 1's for this shape of edit.

**Summary.** Block-Myers is simple to implement (~80 lines including the move post-pass) and produces natural-reading output on `insert` and half of `reorder`. It **fails** on `reword`: any reworded block degenerates to delete+add, and the only way to fix that is to reintroduce Prototype 1's cost-matrix matching. That failure alone makes it unsuitable as the production algorithm — reword is one of the three canonical edit shapes Skrive's diff view has to get right. Useful as a conceptual baseline; not useful as the shipping choice.

**Runtime:** <1ms total across all three fixtures.

## Observations

With all three prototypes run, the picture across fixtures:

| Fixture  | Prototype 1        | Prototype 2 (Zhang-Shasha) | Prototype 3 (Block-Myers) |
|----------|--------------------|-----------------------------|----------------------------|
| reword   | ✅ reworded (d=0.44)| ✅ reworded (d=0.47)        | ❌ delete + add            |
| reorder  | ✅ 6 moves          | ❌ 6 relabels (swap chain)  | ⚠ 3 moves, 3 kept          |
| insert   | ⚠ 3 moves + 3 added | ✅ 3 added (rest kept)      | ✅ 3 added (rest kept)      |

- **Prototype 1 is the only algorithm correct on all three fixtures**, even if it over-reports moves on `insert` (the tail section's position shift surfaces as a move rather than a kept+shift). That over-report is a readability concern, not a correctness concern, and is fixable with a post-pass that collapses contiguous block-level moves with the same offset into a single section-level move — same kind of readability pass the memo already called out for `reorder`.
- **Prototype 2's reorder output is the pivotal data point.** A swap of two sections surfaces as a chain of relabels, never as moves, because classical Zhang-Shasha has no move operation and relabel is unit-cost. Lifting the chain would require swap-chain detection in a post-pass (~50 lines of algorithm-specific code), on top of an already-larger core implementation. That extra complexity buys us nothing on the other two fixtures, and on `reorder` it produces strictly worse output than Prototype 1.
- **The hierarchy advantage stays theoretical.** Zhang-Shasha's pitch ("a paragraph moved into a moved section reads as one move, not two") is not exercised by any existing fixture. Building a fixture that stresses it is a follow-up if dogfooding surfaces the case; without one, Prototype 2's extra machinery has no demonstrated payoff.
- **Block-Myers is ruled out.** The reword failure isn't a tuning issue — it's structural. Fixing it requires re-adding the cost-matrix matching from Prototype 1, which means shipping Prototype 1. No advantage to the indirection.
- **Implementation footprint, debug-build line counts in the prototypes:** P1 ~100 lines, P2 ~350 lines, P3 ~80 lines. Production numbers would differ (P1 needs real Hungarian / Kuhn-Munkres, P2 and P3 stay roughly the same), but the ratio is stable.

## Decision

**Block-hash matching with Hungarian assignment (Prototype 1).**

Rationale:

1. **Correctness across fixtures.** Only algorithm that handles `reword`, `reorder`, and `insert` without failure or structural degradation.
2. **Native move detection.** The cost-matrix approach detects moves as a natural output of the assignment, not as a post-hoc pairing. Zhang-Shasha and Myers both need post-passes of comparable complexity; Prototype 1 avoids them.
3. **Readability post-pass is shared.** Collapsing block-level moves into section-level moves is a concern for all three algorithms; it doesn't tip the choice.
4. **Implementation economy.** Smallest footprint. The production swap from 2-opt to proper Hungarian adds ~50 lines via [`hungarian`](https://crates.io/crates/hungarian) or equivalent; no new auxiliary structures.
5. **Reworded-threshold tuning is the main parameter that needs real-document validation.** The memo's 0.55 threshold is eye-tuned on one fixture; production code should treat this as the first knob dogfooding touches.

**Known follow-ups.**

- **Real Hungarian matcher.** Swap 2-opt local search for Kuhn-Munkres. Pulls in the `hungarian` crate or equivalent; fixture transcripts are unaffected, but production workloads with many same-distance pairs will benefit from optimal assignment.
- **Move-grouping post-pass.** Collapse contiguous block-level moves with the same offset into single section-level moves for renderer readability. Renderer concern, not algorithm concern.
- **Hierarchy-stress fixture.** A fourth fixture that moves a paragraph into a moved section, to validate whether block-level assignment reads acceptably on nested moves or whether a hierarchical follow-up is warranted.
- **Intra-block word-level diff for Reworded ops.** The Block-level reworded op needs a word-level breakdown for the renderer to show "added phrases in sage, deleted phrases struck through." `similar::TextDiff::from_words` drives this; not an algorithm question, a renderer question.

The build outline originally used `git2` as the history source. For projects that aren't git repositories, the history panel has no data to drive it.

**Decision (made in Phase 3.3a).** Both modes. Git for projects that are git repos; Skrive-managed checkpoints for projects that aren't. Mode-based and mutually exclusive per project. cargo test --manifest-path src-tauri/Cargo.toml diff_memo -- --nocapture

to print every algorithm's output for every fixture.
